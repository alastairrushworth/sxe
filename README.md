# SXE — Sparse eXtra Ensembles

**Batch-boosted, holdout-pruned, sparsely re-weighted histogram trees, with a scikit-learn API.**

SXE reaches LightGBM-level accuracy with models that are **5–20× smaller**, and its
predictions are **bit-identical regardless of how many threads you run it on**.

```python
from sxe import SXERegressor

model = SXERegressor(random_state=0).fit(X_train, y_train)
preds = model.predict(X_test)
print(model.summary())
# {'n_iter': 45, 'n_trees_grown': 720, 'n_trees_kept': 304, 'n_leaves': 6068,
#  'model_size_mb': 0.123, ...}
```

> **Status: alpha.** The API is not yet stable, and the published benchmarks are
> single-seed on three datasets. See [Caveats](#caveats) before relying on the
> headline numbers.

## What it does

Features are quantile-binned once into at most 256 histogram bins. A dictionary
of trees is then generated by *batch boosting*: small batches of randomized,
subsampled trees are grown in parallel against the current residual, added with
shrinkage, and early-stopped on a validation fold. Each tree is pruned on its
own out-of-subsample holdout at a randomized strength, so the ensemble spans a
spectrum of bias–variance trade-offs. Finally a single non-negative lasso over
batch-average prediction columns re-weights the boosting trajectory and
physically deletes the batches that contribute nothing — which is where the
size reduction comes from.

The full derivation, the ablations behind each component, and the honest
caveats are in [TECHNICAL_REPORT.md](TECHNICAL_REPORT.md).

## Why you might use it

| | |
|---|---|
| **Small models** | 5–20× fewer bytes than LightGBM at comparable accuracy. Useful when the model ships to an edge device, into a container image, or through a serving path where load time matters. |
| **Reproducibility** | Per-tree RNG seeds derive from the tree index, never from scheduling order, so `n_jobs` is a pure performance knob. Same seed, same predictions, bit for bit. |
| **Parallel structure** | Trees within a batch are independent. Only the batch-level residual update is sequential, so growth parallelises where sequential GBDT cannot. |

## Why you might not

- No missing-value support. NaN and infinity are rejected at `fit` and `predict`
  rather than silently imputed — impute upstream.
- No categorical handling beyond exclusive feature bundling for binary columns.
- Multiclass is one-vs-rest over the binary core, not a native multiclass loss:
  it costs one full ensemble per class.
- Regression and classification both minimise squared error. There is no
  logistic loss and no second-order (Newton) leaf values yet.
- **The defaults are not yet tuned across a broad dataset suite.** The published
  results use per-dataset configurations; see [Tuning](#tuning).

## API

`SXERegressor` and `SXEClassifier` are ordinary scikit-learn estimators — both
pass `sklearn.utils.estimator_checks.check_estimator` in full, so they compose
with `Pipeline`, `GridSearchCV`, `cross_val_score` and `joblib` without
adapters.

```python
import joblib
from sklearn.pipeline import make_pipeline
from sklearn.preprocessing import StandardScaler
from sklearn.model_selection import GridSearchCV

pipe = make_pipeline(StandardScaler(), SXERegressor(random_state=0))
search = GridSearchCV(pipe, {"sxeregressor__learning_rate": [0.05, 0.15, 0.3]}, n_jobs=-1)
search.fit(X, y)

joblib.dump(search.best_estimator_, "model.joblib")   # the trees travel with it
```

Parameter names follow scikit-learn's `HistGradientBoosting*` vocabulary where
the concepts match — `learning_rate`, `max_iter`, `n_iter_no_change`,
`validation_fraction`, `max_bins`, `max_leaf_nodes` — so most knobs need no
translation. The genuinely SXE-specific ones are:

| Parameter | Default | Meaning |
|---|---|---|
| `batch_size` | `10` | Trees grown in parallel per boosting step. `1` recovers ordinary stochastic gradient boosting; one huge batch recovers a random forest. |
| `subsample_range` | `(0.4, 0.75)` | Per-tree row subsample rate. The complement is that tree's pruning holdout, so rates near `1.0` leave little to prune against. |
| `prune_strength_range` | `(1e-3, 1.0)` | Per-tree holdout pruning penalty λ, sampled log-uniformly. Small λ removes only splits that do not help held-out data. |
| `max_depth_choices` | `(4, 5, 6, 7, 8)` | Per-tree depth, sampled uniformly. `0` means unlimited. |
| `min_samples_leaf_range` | `(10, 60)` | Sampled log-uniformly per tree. |
| `max_features_range` | `(0.5, 1.0)` | Candidate-feature fraction, sampled uniformly per tree. |
| `splitter` | `"best"` | `"best"` scans all bins for the optimal cut; `"random"` draws `n_thresholds` random cut-points, trading split quality for member diversity. |
| `bundle_binary_features` | `False` | Exclusive feature bundling for binary columns. Worth enabling on wide one-hot data. |

`n_jobs=None` means *all cores* here, matching other gradient-boosting
libraries rather than scikit-learn's single-core default.

### Diagnostics

```python
model.summary()             # trees grown/kept, leaves, size, timings
model.feature_importances_  # split-gain, weighted by ensemble weight
model.n_iter_               # batches actually run before early stopping
```

## Tuning

The defaults are a reasonable starting point but do **not** reproduce the
benchmark table — those use per-dataset configurations in
[`benchmarks/bench_final.py`](benchmarks/bench_final.py). Distilled guidance
from section 5 of the technical report:

- **Smooth, low-dimensional signal**: fine trajectories. Small `learning_rate`,
  many batches, small `batch_size`, mild subsampling (0.85–1.0),
  `splitter="best"`, `max_leaf_nodes≈63`.
- **High-dimensional or one-hot data**: `max_depth_choices=(10, 12, 14)`,
  `splitter="random"` with `n_thresholds=3`, `bundle_binary_features=True`,
  moderate subsampling.
- **Noisy data with irrelevant features**: aggressive subsampling (0.2–0.4) and
  a large `learning_rate` with tight `n_iter_no_change`. This is where the
  speed comes from.

## Benchmarks

Single core, one fixed 80/20 split, one seed. LightGBM runs near defaults with
early stopping. SXE sizes are a compact-format estimate; LightGBM sizes are
pickled objects, so the leaf counts are the format-free comparison.

| Dataset | Metric | LightGBM | SXE | Leaves LGBM / SXE | Size (MB) LGBM / SXE |
|---|---|---|---|---|---|
| Covertype (binary) | AUC ↑ | 0.9499 | **0.9526** | 60,946 / 66,372 | 6.76 / **1.39** |
| Friedman1 + noise | RMSE ↓ | 1.0945 | **1.0940** | 8,339 / **6,068** | 0.79 / **0.12** |
| California housing | RMSE ↓ | **0.4333** | 0.4469 | 25,823 / **10,033** | 2.40 / **0.21** |

Reproduce with:

```bash
pip install -e ".[bench]"
python benchmarks/bench_final.py --n-jobs 1
```

## Caveats

Read section 8 of the technical report before quoting any of this. In short:
single seed, single split; SXE was tuned per dataset while LightGBM ran near
defaults; model sizes mix a format estimate with pickles. Multi-seed,
multi-dataset evaluation is the next piece of work.
